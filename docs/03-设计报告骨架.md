## 1. 需求分析（1 页）

### 1.1 问题定义
用户输入一句自然语言需求，系统输出可在 KiCad 8 中打开的原理图。中间必须经过两级结构化表示：BOM 与引脚级网表。

### 1.2 用户故事
```
作为 一个没有画板经验的学生，
我想要 用一句话描述我需要的电路板，
以便于 直接得到一份可以在 KiCad 里继续修改的原理图。
```

### 1.3 功能边界（写清楚不做什么，是专业性的体现）
| 做 | 不做 |
|---|---|
| 常见小板（最小系统 / 采集板 / 稳压电源） | 高速信号、射频、多层板 |
| 引脚级连接 + 原理图 | 完整 PCB 布线（作为进阶挑战） |
| 单位换算与器件选型约束 | 供应链价格与库存优化 |

### 1.4 验收标准
给出可量化的指标，例如：
- 三种典型需求，BOM 型号真实存在率 ≥ 90%
- 网表自检（`validate.py`）错误数 = 0
- KiCad 打开成功率 = 3/3
- 单次生成耗时 < 30s

### 2.3 为什么拆成两阶段（BOM → 网表），而不是一步到位？
这是报告里**最重要的一个技术论证**，写满半页：
- 一步生成时，模型要在同一次输出里同时保证"型号合法"和"引脚对应"，错误会互相掩盖；
- 两阶段后，第一阶段的错误（型号编造）可以被 Schema + 白名单独立拦住；
- 阶段间有可检查的中间产物，便于定位问题出在"选型"还是"连线"。

## 3. Prompt 设计思路（2–3 页）

### 3.1 三个 Prompt 的分工
| Prompt | 作用 | 关键约束 |
|---|---|---|
| `system.md` | 定位为"硬件工程师"，只输出 JSON | 禁止解释性文字 |
| `bom.md` | 需求 → 元器件清单 | 型号必须在白名单内、封装必填 |
| `netlist.md` | BOM → 引脚连接 | 每条连接必须 `ref + pin`，网络必须两端以上 |
| `revise.md` | 增量修正 | 只改受影响部分，其余原样返回 |

### 3.2 约束手法的演进（写清"第一版 → 改了什么 → 效果"）

## 5. 失败案例分析（2 页，重头戏）

至少写 4 个，每个按"现象 → 复现 → 根因 → 修法 → 修完还剩下什么问题"五段写。

模板：

### 案例 1：模型编造不存在的电容值
- **现象**：需求"要 100uF 陶瓷电容"，模型输出 `100uF 0603 X7R`——物理上不存在这个容量/封装组合。
- **复现**：`python src/pipeline.py "..." --live`，5 次里出现 3 次。
- **根因**：模型只知道"100uF 是常见容量"，不知道"0603 封装做不到 100uF"。
- **修法**：BOM 阶段加器件白名单（型号 + 封装 + 容值范围），非法值直接拒绝并要求重选。
- **遗留**：白名单维护成本高，只覆盖约 40 个常用器件。

（其他建议案例：漏掉 MCU 每个电源引脚的去耦电容；晶振负载电容算错；网络命名 `VCC` 与 `+5V` 混用导致 KiCad 报多驱动；直接拼 s-expr 导致 lib_symbols 缺失、KiCad 打开空框。）
