# 失败案例台账

> 报告里"失败案例分析"一节的原始素材。原则：**只记真实发生过的，写清
> 触发条件 / 现象 / 定位过程 / 修法 / 是否已加机器检查**。
> 没加机器检查的，下一轮一定会再犯——这是本表的真正价值。

---

## 案例 1 · 去耦电容有一脚悬空，自检层没抓到

- **触发**：Arduino 最小系统板，C3（100nF，VCC 去耦）。
- **现象**：网表自检报"无悬空网络、无重复引脚"，看起来全绿；但生成原理图时
  C3 只画出一个引脚，另一脚不存在。
- **定位**：写原理图生成器时 `numbers[1]` 抛 IndexError 才暴露——C3 的 1 脚
  从未进入任何网络。
- **根因**：自检层只检查了「**网络**只连 1 个引脚」（`net.single_ended`），
  没检查「**器件**只连了 1 个引脚」。两者是不同的错误：
  第一种是网络悬空，第二种是器件悬空。
- **修法**：`validate.py` 新增 `net.open_pin` 检查（R/C/L/D/Y 两脚器件必须两脚
  都进网络）；同时把 C3.1 补进 `+5V` 网络。
- **教训**：检查的粒度要同时覆盖"边"和"点"。这类 bug 靠肉眼看网表 JSON
  几乎不可能发现，做原理图时才炸出来——**下游的可视化是上游的测试用例**。

## 案例 2 · 器件封装名在 KiCad 库里不存在

- **触发**：ESP32 温湿度采集板，DHT11。
- **现象**：KiCad ERC 报 `footprint_link_issues: 在库 'Sensor' 中找不到封装 'DHT11'`。
- **定位**：两次猜错——先写 `Sensor:DHT11`；改成 `Sensor_Humidity:Aosong_...`
  仍报错；最后 `ls <KiCad>/share/kicad/footprints/Sensor.pretty/` 才确认
  真实位置是 `Sensor:Aosong_DHT11_5.5x12.0_P2.54mm`。
- **根因**：**靠记忆写封装名，而不是查库**。模型（包括人）都习惯"猜一个看起来
  合理的名字"，而 KiCad 库里没有模糊匹配。
- **修法**：改成真实库名；并把它作为规则写进 `prompts/bom.md`：封装必须来自
  KiCad 官方库的真实条目，不确定时输出错误也比编造好。
- **教训**：凡是"引用外部命名空间"的字段（封装、符号、库），都必须有一条
  机器校验兜底——这正是 ERC 的 `footprint_link_issues` 干的活。

## 案例 3 · 子符号命名违规，报错完全不提原因

- **触发**：第一版原理图生成器，所有板型。
- **现象**：`kicad-cli sch erc` 只输出「**加载原理图失败**」，没有任何行号或
  字段提示；文件语法本身完全合法。
- **定位**：二分法——依次测试「仅文件头 / +符号定义 / +实例 / +标签」，
  锁定在符号定义段；对照官方示例才发现子符号名必须是「父符号名_0_1」，
  而父符号叫 `pcbagent:RES` 时，子符号必须叫 `RES_0_1`，不能叫 `R_0_1`。
- **根因**：KiCad 的 s-expression 解析器对部分语义错误只返回空泛的加载失败，
  没有诊断信息。
- **修法**：符号工厂统一从 `name.split(":")[-1]` 派生子符号名。
- **教训**：格式类问题要**用二分法定位**，不要盯着整份文件读；另外，
  "语法合法 ≠ 语义合法"，能解析不等于能加载。

## 案例 4 · 关键词匹配把"加个电源灯"判成电源板

- **触发**：需求含"电源"二字但实际是给 Arduino 加一个指示灯。
- **现象**：返回了 5V→3.3V 稳压电源板的 BOM，与需求完全不符，且流水线报成功。
- **根因**：mock 规则用 `"电源" in requirement` 做判断，泛关键词必然误伤。
- **修法**：改为强特征词（"稳压" / "LDO" / "电源板" / "转 3.3"）。
- **教训**：规则匹配的准确率取决于**特征词的特异性**，而不是关键词数量。
  mock 模式的这类误判正是"为什么必须有真实模型 + Schema"的论据。

## 案例 5 · 超范围需求被当成正常需求处理

- **触发**：「帮我设计一块 PCIe 4.0 8 层高速板」。
- **现象**：早期版本直接返回一块 Arduino 最小系统板并报"成功"。
- **修法**：`design.out_of_scope()` 增加能力边界表（PCIe / DDR / 射频 / 多层
  高速），命中则明确拒绝并说明理由与替代方案。
- **教训**：**会拒绝的 Agent 比什么都答应的可信**。报告里要把"能力边界"
  当成设计特性写，而不是缺陷。

## 案例 6 · 修复器把"已连接的脚"当成"悬空的脚"，闭环来回振荡

- **触发**：闭环演示，注入「去耦电容单端悬空」故障（C3 只剩 GND 脚）。
- **现象**：第一版规则修复器把 C3 的**已连接脚**又接到 +5V——引脚冲突出现；
  下一轮冲突修复把它从 +5V 移除，悬空警告又出现；再修复、再冲突……
  4 轮循环输出完全重复，修复器在两个错误之间荡秋千。
- **定位**：`net.open_pin` 的报错文案是「C3 只有引脚 **2** 进了网络」——
  这个 2 是**已连接**的脚，悬空的是另一只。修复器却拿着 2 去补接。
- **根因**：**修复器按字面理解报错文案，没有理解文案的语义**。检测层的
  报错文案是写给人看的，"哪个脚出问题"和"该动哪个脚"不是一回事。
- **修法**：两脚器件悬空时补的是**另一只**（连接脚=2 → 补 1）；同时闭环
  调度器加"一轮没有任何修复进展就止损"的护栏（防止未来同类振荡无限跑）。
- **教训**：①错误信息的**生产者**和**消费者**要一起设计——如果报错结构里
  直接带 `dangling_pin` 字段，这个 bug 根本不会发生；②闭环必须带
  止损护栏和无进展判定，否则"自动修复"可能变成"自动震荡"。
  此教训已反哺：`loop.self_heal()` 对无进展轮次提前终止。

## 案例 7 · 出图美化引入 11 处 endpoint_off_grid

- **触发**：把"一行 4 个"的等距网格改成"主控居中 + 两侧分区"布局，并让画幅随内容自适应（A4/A3/A2）。
- **现象**：图确实好看了，但 ERC 从 0 警告跳到 **11 条 `endpoint_off_grid`**，
  每个引脚各报一句"符号引脚不在连接栅格上"。
- **定位**：为了让内容在图幅里居中，我按包围盒算了平移量 `dx/dy`——这个量是浮点数
  （例如 37.4mm），于是所有引脚坐标都偏离了 KiCad 的 1.27mm（50 mil）栅格。
- **根因**：**KiCad 的连接语义建立在栅格之上**。同一坐标上两根导线才算相连，
  差 0.1mm 就是两根线。而"居中排版"和"落在栅格上"是两个互相冲突的约束：
  居中是连续量，栅格是离散量。
- **修法**：平移后再把所有符号中心吸附到 1.27mm 的整数倍。因为引脚坐标 = 中心 +
  引脚本地位移，而本地位移本身就是 1.27 的整数倍，所以中心一吸附，所有引脚自动落在栅格上。
- **教训**：①"好看"和"正确"在这类生成任务里会打架，必须让**正确性检查在美化之后重跑**，
  不能因为"只是改布局"就跳过；②离散约束（栅格、DRC 规则、Schema 枚举）要把
  **吸附**做在最后一步，而不是指望每个计算公式都自然落在格点上。
  这道检查已经固化进 `scripts/kicad_check.py`，任何布局改动都会被它拦住。
